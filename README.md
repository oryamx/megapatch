# MegaPatch

**Rank what matters, prove it is exploitable by running the exploit against our practice app, and have NVIDIA Nemotron propose the fix. In the recorded runs, the same exploit was then re-run against each patch; this version does not run model-written code.**

Built for the Nebius x NVIDIA Global AI Hackathon 2026 (track: Best Apps and Agents).

> Status: hackathon submission (2026-10-30). This README only describes what exists today.

**Live demo (read-only dashboard):** https://megapatch.streamlit.app/ — it shows recorded real runs, made on 2026-10-10 and 2026-10-12, before this version stopped running model-written code, and opens on the run made with the current judge and approved by a person. If the page says the app is asleep, press *Yes, get this app back up!* (the free hosting sleeps after 12 hours without visits; waking it took about 30 seconds the last time we did it). The recorded runs cannot be replayed without credentials, because they called Nemotron and the Nebius sandbox, but the claims they rest on can be checked offline: `python judge_check.py` runs the exploits against the vulnerable app and a known-good fix, runs the functional tests, and checks that the recorded runs and the re-judge record are consistent with the code and data in this repository.

The five-step strip at the top says what the selected **recorded** run did at each step, and the **Walkthrough** tab follows one finding from its rank to the exploit firing, Nemotron's patch, the **same** exploit re-run against the patched app with the functional tests, and the approval. These are recordings: the current version stops at the patch proposal and does not run it (see "The idea").

Switch runs in the sidebar: *Recorded run with a repaired patch* shows the judge rejecting a patch and Nemotron repairing it from the judge's output; *Run approved by a person* shows a person declining a patch the judge of that time had accepted, and its *Before / after* tab shows a later, stricter judge rejecting that patch.

## The idea

A scanner gives you a long list of findings, all with a CVSS score, so everything looks critical. In our demo, pip-audit reported 124 entries on nine deliberately outdated pinned Python packages, 69 distinct advisories once repeats are removed (the scanner lists some advisories more than once). With the 2 findings Bandit reports in our practice app (3 raw results, one kept per vulnerability class) and 1 from manual review, that is 72 distinct findings covering 62 distinct CVEs, and only one of those CVEs (CVE-2023-4863) is in CISA's KEV catalog. These counts are computed from the scanner files by `ingest.scanner_counts()`, and the dashboard shows them from there. This version of MegaPatch does three things in one flow:

1. **Prioritize with exploitation data, not severity alone.** ScoreRisk is a deterministic rule (not a model): `100 * (0.50*E + 0.30*X + 0.20*S)` where E is exploitability (EPSS, CISA KEV), X is the exposure of the asset, and S is the CVSS base score. A CVSS 9.8 that is almost never exploited ranks below a lower-CVSS finding that is in KEV and internet-facing.
2. **Verify by execution, on our practice app only.** For the top findings, a proof-of-concept exploit we wrote runs against our practice app (`target_app/`): in a Nebius Sandbox in the pipeline, or on your machine in `judge_check.py`. The result is a verdict (`CONFIRMED`, `NOT_REPRODUCIBLE`, or `NOT_VERIFIABLE` for classes without a PoC), not an opinion. The PoCs never target a repository you scan, a URL or an IP address.
3. **Propose a patch.** Nemotron writes the fix from the exploit evidence. **For now it is a proposal, *not executed and not verified*:** model-written code is not run anywhere (`execution_policy.py`), so it is never judged, accepted or exported. No environment here is proven to block outbound network: the Nebius sandbox gives its guest a network unless an operation turns it off (`networking.enabled` defaults to true), the SDK this project uses (`contree-sdk` 0.3.6) does not expose that switch, and `--local` would use your machine's network.

On your own Python repository, the dashboard's local mode scans it read-only (Bandit; by default nothing leaves your machine) and, for one finding type (Bandit B602, a shell command built from a value), can propose a patch with Nemotron: you see the exact text that would be sent, including the code of that one function, and nothing is sent until you consent. The answer is reviewed statically and never run.

**What the recorded runs show (2026-10-10 and 2026-10-12).** The runs in `evidence/` were made before the rule above, and they did the whole loop: the same exploit and the functional tests judged each model-written patch in the Nebius sandbox, the same kind of sandbox where `isolation_check.py` saw one outbound TCP connection to `pypi.org:443` succeed on 2026-10-10, which does not establish the full extent of its network access (see "Safety and scope"); a rejected patch went back to Nemotron for one repair attempt; and each patch the judge accepted reached an approval step before export (`out/patches/*.diff`): a person answered in the two runs made without `--yes`, and the flag skipped the question in the other two (see the table of recorded runs below). The model proposed; the exploit and the tests decided. The dashboard shows those recordings and `judge_check.py` checks them, but they cannot be replayed without credentials, and this version does not repeat that step.

Input is real scanner output: **pip-audit** (software composition analysis) over `scans/requirements.txt` and **Bandit** (static analysis) over our practice app, parsed by `ingest.py`. The scanner outputs are frozen in `scans/` so results are reproducible.

## Quickstart

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate      macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
```

**1. Verify the claim yourself, no credentials needed:**

```bash
python judge_check.py
```

It runs three exploits (SQL injection, OS command injection, path traversal) against the vulnerable practice app (expect `VULNERABLE`) and against a known-good fix (expect `SAFE`), runs the functional tests on both, and checks that ScoreRisk is deterministic. It also checks that every recorded run in `evidence/` matches the current inputs, that the re-judge record is consistent, and runs `check_interactive.py`, `check_export_state.py`, `check_walkthrough.py` (the dashboard rendered headless and compared with the recorded data), `check_language.py` (the same data in English and Spanish), `check_repo_scan.py` (scanning another repository, with fake scanners), `check_patch_proposal.py` (a B602 patch proposal, with fake Nemotron answers) and `check_offline.py` (no model-written code is run, the PoCs stay in-process, a scan is local by default, and a text search finds six network call patterns, such as `urlopen(` and `OpenAI(`, only in the listed modules of MegaPatch's own code: a limited inventory that cannot see network code written another way, in a dependency or in the tools MegaPatch starts, and not a test of the system's isolation). It needs no credentials and only reads the repository. It ends with `ALL PASSED` (exit code 0) only when every check ran in full and passed; if a check script skipped part of its work (it ends `INCOMPLETE` with exit code 2, or prints `SKIP`, for example without the pinned scanners of `requirements-scan.txt`), it ends `INCOMPLETE` (exit code 2), which is not a pass; any failure ends `FAILED` (exit code 1), even if something was skipped too. `check_repo_scan.py` and `check_patch_proposal.py` follow the same rule on their own.

**2. See the ranking (offline, deterministic):**

```bash
python scorerisk.py
python sensitivity.py   # does the ranking survive different weights?
```

Both only print. `--write` regenerates the demo's `evidence/ranking.json` and `evidence/sensitivity.json`.

**3. Run the full pipeline** (needs a Nebius Token Factory account, API key and Sandboxes access):

```bash
pip install -r requirements-pipeline.txt
cp .env.example .env    # then fill NEBIUS_API_KEY and NEBIUS_PROJECT_ID (TAVILY_API_KEY is optional)
python megapatch.py
```

The pipeline ranks the findings, verifies the top 8 in the sandbox, asks Nemotron for a patch for each confirmed one and, for now, records each patch as a proposal, *not executed and not verified*: model-written code is not run (see above), so nothing is judged, accepted or exported. With that rule lifted, it judges the patch in the sandbox, repairs a rejected patch once, and asks you to approve each patch **accepted by the judge** before it is exported. Output goes to a new `evidence/run_<timestamp>.json` (`python megapatch.py --save-as my_run` names it `evidence/my_run.json`), and the approved diffs to a new folder `out/patches/<run name>/`; an earlier record or diff is never replaced. Useful flags: `--top N`, `--yes`, `--eval-only`, `--local`, and `--enrich` (the Tavily evidence step, off unless you pass it).

**4. Look at the result** in a browser:

```bash
streamlit run dashboard.py --server.address 127.0.0.1
```

(`--server.address 127.0.0.1` keeps other machines from opening the page; it does not block the page's own outgoing requests.) The dashboard opens on `evidence/human_approved_run_b.json`, in English; an *English / Español* selector in the sidebar switches the interface language without changing any data (`python check_language.py` verifies that). A *How to use MegaPatch* block says what your team provides, what MegaPatch does and produces, and what a person must review, and a notice makes clear that the page shows recorded runs, not live analysis. A five-step strip states what that run recorded at each step of the loop, and the *Walkthrough* tab follows one finding from its rank to the exploit, Nemotron's patch, the re-test with the same exploit and the approval. The other tabs show the prioritized queue, the before/after proof for each patch, the public evidence for findings that execution cannot verify, and why the order is what it is. It needs no credentials.

**5. Analyze one finding from the dashboard (local, opt-in).** With `NEBIUS_API_KEY`, `NEBIUS_PROJECT_ID` and `MEGAPATCH_ENABLE_INTERACTIVE=1` in your `.env`, the dashboard's *Analyze (local)* tab runs the loop on one finding. **For now the patch is not run**: the tab confirms the finding on the practice app, shows Nemotron's patch as a proposal (*not executed, not verified*) and stops, so there is nothing to approve or export. Once model-written code may run again, it shows each stage as it happens, then the **same PoC** before and after the patch, then waits. **Nothing is exported until you click Approve**, and only a patch the judge accepted can be approved. Each analysis gets its own session id (a UTC timestamp plus random characters, so two sessions started in the same second get different ids); if a collision ever happened, it is rejected without overwriting any file. Your decision is recorded in a new `evidence/interactive_run_<session id>.json` and an approved diff goes to a new `out/patches/<session id>/` folder; existing files are never overwritten. On approval the record is written first with `exported: false` and `export_status: "pending"`, then the diff, and only once the diff is confirmed on disk is the record finalized as `exported: true`. If the process stops in between, the record keeps saying `pending` (never `exported: true`; the diff at `export_target` may or may not exist), and if the diff cannot be written the record says `export_status: "failed"` with the error. A diff is never left without its record, and cleanup only removes files the call itself created. The dashboard's patch detail follows `export_status` (exported, pending, failed, declined): `exported: false` alone is never shown as a refusal by the person, and only `declined` says so. `python check_export_state.py` tests that, including the dashboard rendered headless from a temporary copy. The command-line flow is unchanged. Live runs are off on the public demo (they need your credentials and the explicit flag). The same limits apply as everywhere else: the PoCs call the app in-process, not over HTTP; on 2026-10-10 one outbound TCP connection from the sandbox to `pypi.org:443` succeeded, which does not establish the full extent of its network access; "accepted by the judge" is not "safe in production". `python check_interactive.py` tests these rules with fake model and judge functions, and `judge_check.py` runs it.

## Scan your own Python repository (local, read-only)

**Scope:** Python repositories; the dependencies pinned with `==` in `requirements*.txt` (what pip-audit can check without installing anything); static analysis only. MegaPatch never runs the project's code and does not verify or patch these findings: the PoCs and the patch loop only cover the practice app.

```bash
pip install -r requirements-scan.txt
streamlit run dashboard.py --server.address 127.0.0.1 -- --local-scan
```

`requirements-scan.txt` pins Bandit and pip-audit; a scan refuses to run with other versions and records the ones it used. `--server.address 127.0.0.1` only limits incoming connections: the page answers on this machine only. It says nothing about what the scan sends out: by default nothing, and only the boxes you tick send requests to PyPI and, with threat data, to CISA, FIRST and NVD (listed below under *What leaves the machine*). The scan form is only offered when both are true: the dashboard was started with `--local-scan`, and Streamlit listens on a loopback address (`--server.address 127.0.0.1` or `::1`), so that the operating system refuses connections from every other network interface. Started with `--local-scan` on any other address (or none, which means every interface), the tab refuses to scan or save a declaration and says how to start it; a session that Streamlit reports from another address is refused too, as a second line only, since Streamlit warns that this client address can be spoofed. No environment variable turns the mode on: the public demo is started without arguments, so it never offers it. Saved analyses (project names and results) are shown only in the authorized local mode: when it is off or refused, the tab lists none. **Binding to loopback blocks direct connections from other machines; it does not isolate the page from anything that can reach 127.0.0.1 on this machine:** a reverse proxy, a tunnel or port forwarding (SSH, an editor's port forwarding, ngrok and the like), a container's published port, or other users of a shared machine or server. Through any of those, other people could ask the dashboard to scan a folder. **Do not enable the local scan mode in such deployments:** use it only on your own machine, for yourself, with nothing that forwards its port. In the dashboard's *Your repository (local)* tab:

1. **Type the folder of the project and press *Scan (read-only)*.** The progress is shown step by step.
2. **Declare the exposure:** reachable from the internet, authentication, production, sensitive data. A question left as *Unknown* stays unknown: it is never read as "not exposed", and the score shows the range it could add. Each declaration is saved as a new file; earlier ones are kept.
3. **Read the two queues**, each finding with its file and line (the line of `requirements*.txt` that pins the package, or the line Bandit flagged), and pick one to see what supports its position.

The same without the dashboard:

```bash
python repo_scan.py PATH/TO/REPO
python repo_scan.py --show PROJECT
python repo_scan.py --declare PROJECT internet_facing=yes requires_auth=unknown environment=production sensitive_data=no
```

- **Two queues, because a dependency advisory and a code finding have no common scale.** Dependencies are ranked with ScoreRisk (the demo's rule and weights). A value that is not available is not replaced by a default: it becomes an interval (no EPSS: E between 0 and 1; no CVSS: S between 0 and 1; an exposure question not answered: the X it could add), so the score is a range; the queue follows the guaranteed minimum, and a row whose position could change once the missing value is known is marked *provisional*. Code findings are ranked by Bandit's own severity, then its confidence, with test code after the other findings of the same level; Bandit's ratings are not CVSS and no number is computed for them. CVE, CWE, CVSS and EPSS are shown only when available.
- **Nothing from the repository runs, and its folder does not change.** Not even git: the commit is read from the `.git` files, because a repository's own git configuration can make git run commands. Only when you ask for the dependency check, pip-audit reads a copy of the pinned lines (`--no-deps --disable-pip -s pypi`: nothing is resolved or installed); without it, each pinned line is listed as not audited; `-r` files inside the repository are followed, and unpinned or option lines are listed as not audited, and what a line can carry as a credential is masked before it is stored or shown (a URL's user and password, the values of its query parameters, its fragment, and option values); the dashboard masks again what it shows, for scans saved by an earlier version. `pyproject.toml`, `setup.py`, `Pipfile` and lock files are listed as found but not read. Bandit only parses the `.py` files. Left out: `.git` and other version-control folders, every file and folder whose name starts with `.env` (such as `.env`, `.env.local` or `.env.py`: never read, and not given to Bandit), virtual environments (`.venv`, `venv`, or any folder with a `pyvenv.cfg`), and build and cache folders. Every file of the folder is listed (path, size, modification time) before and after the scan, and the result says whether anything changed.
- **What leaves the machine: nothing, by default.** Two boxes in the form (or `--audit-dependencies` and `--threat-data` on the command line) are off until you tick them, and each says what it sends: the dependency check sends the name and version of each pinned package to PyPI's JSON API (pip-audit); threat data, for the CVEs that check finds, downloads the CISA KEV catalog (nothing is sent) and sends the CVE ids to FIRST EPSS and, one per request, to NVD (roughly 7 to 12 seconds per CVE without an `NVD_API_KEY`: an approximate figure that depends on NVD's response time; 21 CVEs took 3 to 4 minutes in our tests). Nothing is downloaded when there is no CVE. The scan itself sends no source code and no file names, and nothing to Streamlit, Nebius, Tavily or a model. The one exception in this tab is a patch proposal you authorize (below): it sends Nemotron the exact text it shows you before you consent, and that text includes the code of one function. Without threat data, the dependency scores are ranges.
- **Nothing is overwritten.** Every scan gets a new id and a new folder `analysis/<project>/scans/<scan id>/` (`scan.json` is written last, so an interrupted scan is never shown as complete), and every exposure declaration is a new file in `analysis/<project>/exposure/`. Bandit's code excerpts are not kept, the value of a suspected hardcoded password is masked, and the dashboard shows the folder's name, not its full path. `analysis/` is not committed, and the demo's `scans/`, `data/` and `evidence/` are never written. Without `--local-scan` (as on the public demo) the tab only explains how to run it.
- `python check_repo_scan.py` tests all of this offline: the local-only default (Bandit alone, nothing queried outside, git not run, the two boxes unticked), the opt-ins with fake pip-audit output and a fake download, and the in-process network detector (`no_network.py`, with the limits listed under "Safety and scope"), which fails the check if anything tried to reach another host; the real Bandit when installed (without it, the check ends `INCOMPLETE`, exit code 2, never `ALL PASSED`), a sample repository with a `.git`, a `.env` holding a fake secret, two virtual environments, and code that leaves a marker file if it ever runs; it also renders the tab headless and checks that the demo's files are unchanged.

### Propose a patch for one B602 finding (NVIDIA Nemotron, statically reviewed, not tested)

For one finding type only, Bandit **B602** (`subprocess` with `shell=True`, CWE-78), the explanation of the finding offers a patch proposal. It is the bridge between your repository and Nemotron, and it is deliberately narrow:

- **Simple commands only.** The command must be literal words and whole values joined with `+` or an f-string. Pipes, redirections, wildcards, variables, substitutions, quotes, a value glued to other text, or a command built elsewhere are refused as not compatible, because an argument list could change what the command does.
- **You see exactly what would be sent, and the estimated cost, before anything is sent.** Only the function that contains the flagged line goes, with Bandit's message: no other code, never the repository, `.env*`, `.git` or a virtual environment. If the function looks like it holds a credential, sending is blocked. The send button stays off until you tick the consent box. The request goes to NVIDIA Nemotron on Nebius Token Factory (`llm.py`, which logs tokens and estimated cost) and needs `NEBIUS_API_KEY` in `.env`.
- **Reviewed statically on a disposable copy of that one file, never run.** The checks: the file parses; only the target function changed (same name, arguments and decorators); no `subprocess` call in it uses `shell=True`; the argument list holds the original command's words in the same order, each value as its own element; Bandit no longer reports B602 there and reports nothing new of medium or high severity (low-severity notes such as B603 and B607 are listed). A proposal that fails cannot be approved. The argument list may be written in the call, or in a local name assigned once, before the call, to a list literal and used nowhere else (a reassignment, an `append`, an item change or an alias is refused); every call the function makes must be one of a short list of recognized forms, and it may not start more processes than before. The forms: `subprocess.call/run/check_call/check_output/Popen` on an unaliased `import subprocess`; `os.path.*` and `os.fspath`; a few builtins; names from `flask` and `pathlib`; and only these methods: `startswith`, `resolve`, `is_relative_to`, `is_file` and `is_absolute` on a local name or a computed value (one level), `resolve` and `route` on a module-level constant built from those modules, and `args.get` (also `form.get`, `values.get`) on Flask's `request`. Anything else fails that check with the reason: an import or alias such as `from os import system`, a dynamic call (`getattr`, `__import__`, a function kept in a local name), a module-level function it cannot follow, `os.popen`, `subprocess.getoutput`, or any other method, such as `runner.run(...)` or `request.args.get(...).run(...)`. The list is matched by name, not by type: an object of an unexpected type whose method has an allowed name (for example a parameter with its own `resolve()`) is not detected. It is a closed list for this narrow case, not an analysis of what any Python code can run. Observations, which are not checks, note what a reader should see, such as a removed comment or an error response returned without a status code (HTTP 200).
- **Removing `shell=True` is not enough when the value names a file.** It could still point anywhere, or be read as an option of the program. You can declare an **allowed folder**: a name the file already defines at module level, such as `BACKUP_SOURCE = Path(...)`. The request then also asks Nemotron to reject empty, absolute and `-...` values, resolve the path (which follows symbolic links), keep it inside that folder, require an existing file, and pass the resolved path, not the raw value, after a `--` element. The review then checks each condition of that contract on its own, so that leaving out any one of them fails its own check: the empty, `-...` and absolute values are rejected before the command runs; the path is `<folder> / <value>` with `.resolve()`; there is a rejection unless it is inside `<folder>.resolve()` (`is_relative_to`); there is a rejection unless it is an existing file (`is_file()`); and exactly that checked path is passed right after one `--`, never the raw value. The review accepts only a short, closed list of forms (`GUARD_TERMS` in `propose_patch.py`); anything else fails closed, so the proposal cannot be approved or exported. A rejection counts only when the code's structure proves it is unconditional and comes before the command: an `if` that is a statement of the function itself, before the first statement that holds a process call, whose branch ends with `return` or `raise`, and whose test is one of these terms or several joined by `or`: `not v`, `v == ''`, `len(v) == 0`, `v.startswith('-')`, `Path(v).is_absolute()` (or another `pathlib` type), `os.path.isabs(v)`, `not c.is_relative_to(r)` and `not c.is_file()`, where `v` is the value, `c` the checked path (a name assigned once to `(<folder> / v).resolve()`) and `r` `<folder>.resolve()` or a name assigned once to it. Every name a term relies on must be bound exactly as expected in the whole function: `v`, `c` and `r` once, before the check; any other (`Path`, `os`, `len`, the folder) never, whether by a second assignment, a loop or `with` variable, `:=`, `+=`, `del`, a parameter, an import or a nested definition. So these fail: a `return` nested under another condition or only in an `else`, a test that also needs another condition (`and`), a `raise` caught by a `try`, a check inside a loop, a `with`, a `match`, another `if` or a nested function (called or not), a check after the command, and the value, the folder or the checked path bound again, or a name such as `Path` shadowed. The rule itself is tested on MegaPatch's reference implementation (`confined_path()`): absolute paths, `..`, a link that leaves the folder, option-like names, an empty value, a folder and a missing file are rejected, and a file inside the folder is accepted. A proposal is only checked, by reading its code, to follow that structure; it is never run.
- **A proposal, not an accepted patch.** Nothing from the project is run, so the proposal is labeled *statically reviewed, not tested in the application*. That is weaker than the practice app's verdicts, where the same exploit and the tests run against the patch in the sandbox. A person approves or rejects it; only an approval exports the diff, to `analysis/<project>/patches/<proposal id>.diff`. The project itself is never modified, and each proposal and decision is written once in `analysis/<project>/proposals/<proposal id>/` (it holds the text that was sent, and stays on this machine).
- **Bound to the exact file.** The text to send records the sha256 of the bytes of the file it came from. If the file changes before sending, nothing is sent; if it changes while the answer is awaited, the answer is kept but gets no review and no diff; and approving checks the file again, so a diff is never exported for a file that is no longer the version it was made from (a proposal recorded before this check does not hold the version and cannot be approved; a new `--rereview` of the original request records it). The decision is saved first, with the sha256 of the approved diff; then the diff is put in place. An approval is in one of four states, named the same way in English and Spanish:
  - **Exported** (*Exportada*): the diff is in place with exactly the approved text. The only finished approval; still not tested in the application.
  - **Pending** (*Pendiente*): approved, but the diff is not in place (the export failed, or the process stopped between saving the decision and putting the diff in place). Never shown as a finished approval. *Retry the export* puts it in place and removes leftover temporary files; the button stays off until the folder typed above holds the source file in exactly the approved version, so it is never a button that can only fail.
  - **Obsolete** (*Obsoleta*, `stale`): the diff is not in place and the source file in that folder has changed since the approval. It is not exported and there is nothing to retry: make a new proposal for the current file. It is worked out from the file each time, not stored: if the file is put back byte for byte as it was approved, the approval is pending again.
  - **Conflict** (*Conflicto*): another file is already at the diff's name. It is never replaced; a person must check it.

  Every record (`proposal.json`, `decision.json`, and the exported diff) is written to a temporary file and put in place with a **hard link**: complete or not at all, and never replacing an existing file. An interruption can leave a temporary `.partial` file, never a cut-off record. A record that cannot be read (cut off by an earlier version of MegaPatch, or damaged) is skipped, listed in the dashboard as unreadable, and left untouched; it never stops the page. Hard links depend on the file system: NTFS, ext4, APFS and most local file systems have them; FAT32, exFAT and some network shares do not. Without them, MegaPatch checks before sending and refuses: "this file system does not support hard links ...: nothing was sent or recorded"; approving or rejecting a proposal there ends with "the decision ... could not be saved (...): nothing was decided or exported", and the proposal stays undecided. Nothing reports a success in that case. (This outcome is simulated in `check_patch_proposal.py` by making `os.link` refuse; it was not run on a real FAT or exFAT volume.)
- Without the dashboard: `python propose_patch.py PATH/TO/REPO --project NAME --finding FINDING_ID [--allowed NAME]` shows what would be sent and sends nothing; `--send --i-consent` sends it. `--rereview PROPOSAL_ID` reviews a recorded answer again with the current checks, into a new record: no request is sent and the original record is not changed.
- `python check_patch_proposal.py` tests all of this offline with fake Nemotron answers (a correct one and five wrong ones), a clean project and a synthetic service with two B602 findings (one simple, one through a pipe), consent, a function holding a fake credential, the allowed folder (the rule on real files and a link, and four incomplete confined answers), approval, rejection, a file changed since the scan, rejections that are not unconditional (nested under a condition, inside another `if`, a `try` or a nested function, or after the command), a file changed after the text was prepared, while the answer was awaited and before the approval, an export that stops part way (pending, then retried, with no folder, with another version of the file), a source file changed after the approval (obsolete), a file that appears at the diff's name, an interruption while writing `proposal.json`, cut-off records, a file system without hard links (simulated), nineteen forms of rejection the review cannot prove, and the dashboard section (pending, obsolete and exported approvals, and a cut-off record); it checks that the projects never change and none of their code runs. It needs the pinned scanners: without them it ends `INCOMPLETE` (exit code 2), never `ALL PASSED`.

## Action bands

Each finding gets a band named after CISA's SSVC outcomes (Act, Attend, Track\*, Track). This is a **simplified, project-specific rule table, not CISA's SSVC decision tree**, defined in `bands.py`:

| Band | Rule |
|---|---|
| Act | Exploit confirmed in the sandbox, or in CISA KEV and internet-facing |
| Attend | In KEV but internal, or EPSS at or above a project parameter (0.50) |
| Track\* | Internet-facing with no exploitation evidence |
| Track | No strong signal |

Every band shows its basis. Asset exposure is declared in `data/assets.json`, so a band for a finding that was not verified by execution (for example the KEV-listed libwebp issue reported through Pillow) is built from KEV/EPSS plus declared exposure, not from an exploit run.

## What the data is (and is not)

- **Real:** CVE identifiers, EPSS (FIRST), CISA KEV membership and CVSS base scores (NVD), frozen in `data/threat_data.json` so results are reproducible. Refresh with `python fetch_threat_data.py`.
- **Real scanner output, deliberately chosen input:** pip-audit ran over nine pinned packages that we picked because they are old (so the scanner has a lot to say), and Bandit ran over our own practice app. Bandit flagged two of our three vulnerability classes; the path traversal was added from manual review and is labeled as such.
- **Declared, fictional context:** which asset each package or file belongs to and how exposed that asset is (`data/assets.json`). Weights and constants in `scorerisk.py` are starting points, not validated values; `sensitivity.py` checks which conclusions depend on them (it varies the weights, not these declared inputs).
- **Verifiable in the MVP:** only the three vulnerability classes of our own practice app (`target_app/`). Other findings are ranked but reported as `NOT_VERIFIABLE`, never as safe. Findings of another repository scanned with `repo_scan.py` are ranked only: not verified and not patched.
- **Not measured yet:** we do not claim any precision figure for the ranking.
- **The public-evidence step is not reproducible run to run.** Web results and the model's summary can change between runs (we observed it). That is why it never enters the score; each run stores the sources and the summary it saw.
- **The judge only judges what the tests cover.** A patch can pass the PoC and the tests and still differ in behavior outside them. For example, a "fix" that blacklists the exact payload used by the PoC would pass it; the PoC tests one payload per class, not every payload.
- **The path traversal check was strengthened after the recorded runs, because a person declined a patch the judge had accepted.** That patch used a `startswith` comparison on path strings. The first PoC only tried `../secret.txt`; the PoC now also tries `../public_backup/backup.txt`, a sibling directory whose name starts with `public`, and `judge_check.py` includes a `startswith` patch that must be rejected. `golden_run.json`, `run_with_repair.json` and `human_approved_run.json` predate this check and `human_approved_run_b.json` was made with it; each new run stores a `judge_fingerprint`, a hash of exactly these nine files: `harness.py`, `test_target_app.py`, `target_app/app.py`, `judge.py`, `sandbox_judge.py`, `catalog.py`, `poc_sqli.py`, `poc_cmdi.py` and `poc_path.py` (what it does not cover is listed in the bullet below), and the dashboard tells you when a run was judged with a different version.
- **A separate re-judge record exists** (`evidence/rejudge_<judge fingerprint>.json`, made by `python rejudge.py`). It rebuilds each patch stored in `golden_run.json`, `run_with_repair.json` and `human_approved_run.json` (`human_approved_run_b.json` was made with the current judge and is not part of this record) from its diff, checks that the diff round-trips against the vulnerable app of that time, applies the same change to the current app and judges it again in the sandbox with the current PoCs and tests. For every patch it stores the run file and its hash, the diff hash, the CWE, the original verdict, the verdict of the current judge, the judge fingerprint, the sandbox's package versions and the judge's output. It is not part of any recorded run, exports nothing and calls no model. Result: of the 9 recorded patches, 8 are still accepted and 1 (the path traversal patch that a person declined to export) is rejected by the current judge. `python judge_check.py` verifies the record: that each result points at its run by hash and the run is unmodified, that each `diff_sha256` equals the diff stored in that run, that the original verdicts copied into the record equal the run's own data, that every `verdict_changed` flag follows from them, that each new verdict follows from its stored `poc_exit` and `tests_exit` by the acceptance rule in `judge.py`, that the record covers exactly every patch of those three source runs once (no omissions, no duplicates), and that the summary totals add up. **If the judge changed after the record was made, the check fails and prints a `STALE RE-JUDGE RECORD` notice** instead of ending in `ALL PASSED`; the fix is to re-run `python rejudge.py --force`.
- **What the judge fingerprint covers, and what it does not.** It hashes the PoCs, the functional tests, the harness, the vulnerable app, `catalog.py`, `sandbox_judge.py` and `judge.py` (the acceptance rule and the local executor). It does not cover the packages installed inside the sandbox at run time (`flask` and `pytest` are installed unpinned; the re-judge record stores the versions it saw), the `contree-sdk` version, or Nebius's platform behavior.
- **Exploitability uses EPSS and CISA KEV only.** "A public exploit exists" is not a separate signal in the score. The sandbox PoC covers that question for the findings we can execute.
- **The demo's scanner outputs are frozen fixtures.** `ingest.py` parses real pip-audit and Bandit JSON, but the demo pipeline does not run the scanners itself nor clone a repository; `repo_scan.py` scans another repository into `analysis/<project>/scans/<scan id>/` without touching them. Refreshing the fixtures replaces the frozen files the recorded runs were made with (their inventory fingerprint will no longer match): `pip-audit -r scans/requirements.txt --no-deps --disable-pip -f json -o scans/pip_audit.json` and `bandit -r target_app -f json -o scans/bandit.json`, then `python fetch_threat_data.py`.
- **The PoCs call the app in-process** through Flask's test client. They show that the code executes the payload and that a patch blocks it; they do not test network reachability, and `NOT_REACHABLE` is not implemented.
- **The safety guarantees apply to the default path.** `--yes` skips every human approval question and `--local` runs the judge on the developer's machine instead of an isolated sandbox. Both exist for development and offline checks; every recorded run is labeled with how it was approved (`approval` in `evidence/*.json`). `golden_run.json` and `run_with_repair.json` were made with `--yes`; the dashboard opens on `human_approved_run_b.json`, which was not.
- **Sandbox runs from one checkpoint, but patches do not compete yet.** Dependencies are installed once and every judge run starts from that checkpoint; we generate one candidate per finding (plus one repair attempt), not several competing candidates.

## Safety and scope

- Exploits and PoCs only ever target the bundled practice app (`target_app/`), in-process through Flask's test client: never a URL or an IP address. No third-party system, repository or account is attacked. A repository you scan is read, never run (not even git), and the scan sends none of its code. Only a patch proposal you authorize sends code: the exact function shown to you before you consent, to Nemotron on Nebius Token Factory.
- **Model-written code is not run, anywhere, for now** (`execution_policy.py`; no flag or environment variable turns it on): neither in the Nebius sandbox nor with `--local`. A patch from Nemotron is a proposal, *not executed and not verified*. `rejudge.py`, whose only job is to run recorded patches again, refuses; `sandbox_spike.py` skips its candidate.
- External services the project calls, each only when you run that part: Nebius Token Factory (Nemotron: the pipeline, the *Analyze (local)* tab, and a patch proposal you consent to); Nebius Sandboxes (the PoC on the practice app, in the pipeline); Tavily (the pipeline's evidence step, only with `--enrich`: a `TAVILY_API_KEY` alone does not turn it on); PyPI (a scan's dependency check, a box you tick); and CISA KEV, FIRST EPSS and the NVD API (a scan's threat data, a box you tick, or when refreshing the demo's data). `isolation_check.py`, a gate script that no routine check runs (`check_offline.py` verifies that), opens one TCP connection to `pypi.org:443` (a host `pip` already uses) and sends no application data, only to observe whether outbound traffic is possible.
- No real credentials inside the sandbox; the practice app only contains fake secrets.
- What would allow model-written code to run again: a sandbox operation started with `networking.enabled = false` (the dependencies prepared beforehand, in an operation that runs no candidate, since a saved image does not keep the network setting) and, inside that same operation, a check that `/sys/class/net` holds only the loopback interface, before the candidate runs (Nebius's documentation, "Prepare inputs, then verify with networking disabled"). A sandbox that accepts no incoming connection proves nothing about outgoing ones, and a static filter of the candidate would be extra defense, not proof. For this submission it stays off, and the recorded runs are the only ones where a patch was judged: there, model-written code ran automatically in the sandbox, and each patch **accepted by the judge** reached an approval step before it was exported (a person answered in the two runs made without `--yes`).
- The checks (`judge_check.py` and every check script) use mocks for every service, so they make no service call. They also install `no_network.py`, a **detector, not a barrier**: in the check's own Python process, from the moment it is installed, it refuses name lookups (`getaddrinfo`, `gethostbyname`), TCP and UDP connections and UDP datagrams to any host other than this machine, before anything is sent, and the check fails if anything tried. It does not cover child processes that do not install it (Bandit, pytest, the PoCs, git and pip when a check runs them), code that took a reference to the original functions before it was installed or uses the C module `_socket` directly, connections that do not go through `socket.connect` (asyncio's Windows Proactor loop, C extensions with their own network code), other address families, or anything at the operating-system level: there is no system network block in the checks.
- What was observed inside the sandbox (`python isolation_check.py` writes `evidence/isolation_check.json`; these are observations, not guarantees):
  - its environment variables are the base image's own, with no Nebius or Tavily variables; we pass no secrets into it;
  - its working directory contains only the files we upload;
  - we looked for the developer's drives at `/c`, `/mnt` and `/host` and found nothing there; the sandbox's root filesystem is a `virtiofs` mount supplied by Nebius's infrastructure. That is a statement about the paths we checked, not proof about the platform's internal isolation;
  - **on 2026-10-10, one outbound TCP connection to `pypi.org:443` succeeded** (a host `pip` uses). That does not establish the full extent of the sandbox's network access. Code runs as root inside the sandbox.

  So "isolation" here means "nothing sensitive is placed in it and it is not our machine", not "it cannot reach the internet".
- Defensive security lab: the goal is to shorten the time between finding and fixing, not to enable attacks. The PoCs only target the bundled practice app and only echo a marker or read its own fake file.
